CORS: de poortwachter van je browser

Waarom je server antwoordt maar je code niets ziet

Je JavaScript vraagt data op bij een server op een ander domein. De server antwoordt netjes met 200 OK — maar je code krijgt niets te zien, alleen een rode CORS-fout. Toch is het niet de server die blokkeert: het is je eigen browser, die het antwoord tegenhoudt voordat jouw code het mag lezen. Stel een aanroep samen, druk op verstuur, en kijk waar het precies misgaat.

Scenario's

Wat gebeurt er nu echt?

Browsers hanteren standaard de Same-Origin Policy: JavaScript op app.jouwsite.nl mag geen antwoord lezen van een andere origin. Een origin is de combinatie van protocol + domein + poort — dus https://api.jouwsite.nl is al een andere origin dan https://app.jouwsite.nl. Zonder die regel zou een kwaadwillende pagina jouw ingelogde sessie bij de bank kunnen misbruiken.

CORS (Cross-Origin Resource Sharing) is de manier om die regel veilig te versoepelen. De browser verstuurt de aanroep, maar kijkt daarna naar de antwoordheaders van de server om te beslissen of jouw code de data mag zien. De sleutelheader is Access-Control-Allow-Origin.

Simpele aanroep — de server doet het werk tóch

Een simpele aanroep (een gewone GET of POST met formuliertekst, zonder eigen headers) gaat meteen naar de server. De server verwerkt hem — en dat is de valkuil: ontbreekt de juiste Access-Control-Allow-Origin, dan blokkeert de browser alleen het antwoord. Jij ziet een CORS-fout in de console, maar in je backend-log staat gewoon 200 OK. De actie is dus al uitgevoerd.

Preflight — eerst kloppen, dan pas binnen

Bij een gevaarlijker aanroep (PUT, DELETE, JSON, of een eigen header) stuurt de browser éérst een korte OPTIONS-aanroep: de preflight. Die vraagt: “mag ik straks een DELETE sturen vanaf jouwsite.nl?” Pas als de server met de juiste Access-Control-Allow-Methods en -Allow-Origin antwoordt, gaat de echte aanroep eropuit. Zegt de server nee, dan wordt de echte aanroep nooit verstuurd — en gebeurt er dus ook niets op de server.

Twee addertjes

Stuur je cookies mee (credentials), dan mag Access-Control-Allow-Origin: * niet meer — de server moet jouw exacte origin teruggeven én Access-Control-Allow-Credentials: true sturen. En de Origin-header wordt door de browser zelf gezet: JavaScript kan hem niet vervalsen.

De grote gedachte: CORS is geen slot op je server, maar een poortwachter in de browser. curl, Postman of een backend trekken zich er niets van aan — zij zijn geen browser. CORS beschermt dus niet je server, maar de gebruiker die jouw site bezoekt.
